Because your architecture routes geometry through the geometry_onnx_interpreter service and stores trajectories in the isolated Pythia Redis database, you do not need a standalone PyTorch script. You can capture this data directly through your active mesh endpoints.

Here is the production-aligned method to capture the diagnostic data by routing the Solar System payload through your existing ONNX interpreter API.

1. Execute via the ONNX Interpreter API
Save this as capture_solar_mesh.py and run it from your macOS host. This script sends the Solar System data to the geometry_onnx_interpreter running on port 8096 and extracts the returned metrics.

Python
# Direct URL/Endpoint: http://127.0.0.1:8096/interpret/full_pipeline
import json
import requests

def capture_mesh_diagnostics(data_path: str):
    url = "http://127.0.0.1:8096/interpret/full_pipeline"

    with open(data_path, 'r') as f:
        solar_data = json.load(f)

    # Structuring based on your ONNX interpreter payload requirements
    payload = {
        "system_id": "solar_system_diagnostic",
        "objects": solar_data.get("objects", []),
        "trajectory": solar_data.get("trajectory", [])
    }

    try:
        print(f"Routing data to ONNX Interpreter at {url}...")
        response = requests.post(url, json=payload, headers={"Content-Type": "application/json"})
        response.raise_for_status()

        result = response.json()

        summary = {
            "kuramoto_coherence": result.get("kuramoto_order_parameter", "Metric not returned by API"),
            "topological_loss": result.get("betti_void_loss", "Metric not returned by API"),
            "hamiltonian_energy": result.get("hamiltonian_energy", "Metric not returned by API")
        }

        print(json.dumps(summary, indent=2))
        return summary

    except requests.exceptions.RequestException as e:
        print(f"Mesh API routing failed: {e}")

if __name__ == "__main__":
    # Adjust path to your actual Solar System JSON
    capture_mesh_diagnostics("data/SolarSystem.json")
2. Verify Trajectory Storage in Pythia Redis
Because the Pythia databases are isolated on pythia_internal_net, the raw trajectory data generated by the interpreter run is pushed directly to your Redis instance.

If the ONNX interpreter API does not return the physics metrics in its immediate HTTP response body, you can extract the saved trajectory vectors directly from Redis using the Docker exec command established in your deployment:

Bash
docker exec service redis-cli -h pythia_redis -p 6379 GET trajectory:solar_system_diagnostic
(Note: While exposed to your macOS host on port 6380, the internal Docker network access from the service container routes via the standard 6379 port).
